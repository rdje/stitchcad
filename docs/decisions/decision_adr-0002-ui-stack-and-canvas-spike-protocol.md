# ADR-0002 — the chrome is decided, the canvas is not, and the spike that decides it is written down first

- **Type:** `decision` (ADR-0002 in `ROADMAP.md` §5)
- **Date:** `2026-09-30` (absolute); the roadmap reserved canvas hosting to a G1 spike, and §11's G0 exit
  clause requires the ADR recorded, so what is recorded here is a decision *structure* plus the protocol
  whose evidence completes it
- **Status:** `active` for the chrome, the dev shell and the TypeScript ban; **`proposed` for canvas
  hosting**, which `G1-SLICE.13` settles by measurement and moves to `active` citing its own data
- **Owner / source:** leaf `G0-CONTRACT.11`, from roadmap §5 ADR-0002, §7.3 (the three runtime profiles)
  and §11 G1; consumed by `G1-SLICE.13` (the spike) and `G1-SLICE.14` (the dev shell)

answers: "which UI stack does StitchCAD ship?" · "why is canvas hosting not decided yet?" · "what does the canvas spike measure?" · "what makes a topology win?" · "what happens if no topology passes?" · "why is a DOM canvas still a candidate?"

## The decision

**Four things are decided now and one is deliberately not.** Chrome: Tauri with a TypeScript/React
front end, and no business or domain logic in TypeScript, enforced by convention *and* CI. Dev shell:
egui/iced for the Stage 1–4 internal tools, explicitly not the product UX. Canvas hosting: **not
decided** — three topologies exist, the choice is a measurement, and this record writes the measurement
down before anybody runs it, so the outcome cannot be argued after the fact. Flutter stays rejected for
the roadmap's reason (a second language across the semantic graph, a weaker CAD-viewport story), and
Slint stays the named fallback if "zero non-Rust" ever becomes a hard constraint.

The canvas question is decided **twice, once per runtime profile**, because a topology that is
native-only can win the native decision and be ineligible for the browser one (§7.3's profiles are not
one target). The protocol's rule R4 then prefers one topology for both when it may, because one renderer
is one code path and one conformance surface.

## The three topologies, and what each would have to be true

| Topology | Applies to | The hypothesis it tests |
| --- | --- | --- |
| WebGPU inside the webview | native and browser | one renderer, one code path, and the webview's WebGPU is complete enough on all three desktop OSes |
| native wgpu surface composed with HTML chrome | native only | a native surface beats a webview for a CAD viewport, at the cost of two renderers and a composition seam |
| DOM canvas | native and browser | the platform canvas is fast enough and precise enough, which the roadmap refuses to assume in either direction |

The roadmap's own caution is the reason all three are measured: *"Custom wgpu, not DOM canvas" is a
hypothesis to test, not an axiom (coordinate precision is a renderer-design concern, not a DOM
property).* A protocol written to confirm a preference is not a protocol, so the correctness gates below
are the ones a DOM canvas could pass and a sloppy wgpu renderer could fail.

## The corpus, declared before the measurement

The spike measures a **declared synthetic corpus**, because G1 has no geometry kernel yet (that is G2) and
a corpus invented during the spike is a corpus chosen to suit a result:

| Quantity | Declared value | Why |
| --- | --- | --- |
| pieces | 16 | the bound of the largest garment set the envelope names (roadmap §3.2 as `G3-GRADING.5` and `.15` will draft it: trousers with pockets, a darted bodice, a sleeve pair, a classic collar, facings) |
| boundary vertices per piece | 400 | a trouser leg's crotch and hem at the T2 chordal bound of 100 µm for a polyline-only surface |
| annotations | 4 labels, 6 notches, 1 grainline, 3 internal lines per piece | the fixture's own density (reference skirt §7), so text and marks are in the measurement and not added later |
| pick probes | 200 points with the entity id each must resolve to | correctness, not speed, is what picking can silently lose |
| snap probes | 200 points with the mathematically nearest entity named | the same, for snapping |
| fidelity path | zoom 1:100 → 40:1 → 1:100, 1 000 round trips | drift is the failure a screenshot cannot show |

The corpus is generated by a script at G1, checked in beside the results, and its declaration here is what
makes two runs comparable. **Re-run trigger:** if a G3 garment exceeds 16 pieces or 400 vertices per piece,
the spike is re-run at the larger bound, because a verdict measured under the envelope is a verdict about
a smaller product.

## The gates

Each gate is a hard disqualifier, not a score; the data plane is
`docs/tasks/artifacts/canvas_spike/spike_gates.tsv` (thresholds), `spike_topologies.tsv` (which topology is
a candidate in which profile) and `spike_rule.tsv` (the margin, the tiebreak order, the fallback), all of
which the verdict instrument reads rather than restating in code. `results.tsv` is the file `G1-SLICE.13`
fills in, and it is empty on purpose: until rows exist the instrument prints `PENDING`, which is why this
record's status is `proposed` for the canvas half.

| Gate | Requirement | What it protects |
| --- | --- | --- |
| capability | runs at all in the profile, on all three desktop OSes | a topology that cannot ship is not a candidate |
| pick correctness | 200 of 200 probes resolve to the declared entity | a hit test that is approximately right selects the wrong edge |
| snap correctness | 200 of 200 probes snap to the mathematically nearest entity | snapping is the interaction a patternmaker feels as trust |
| coordinate fidelity | screen→world→screen error ≤ 0.5 px across the whole zoom range | the precision question the roadmap refuses to assume |
| fidelity drift | exactly 0 after 1 000 round trips | units §1's "no accumulated drift", applied to the viewport |
| frame time | p95 ≤ 16.7 ms (60 Hz) during scripted zoom and pan | a hitch is what a user feels, so p95 and not the median |
| memory | peak ≤ 1 024 MB on the corpus | an unbounded renderer is a product defect at a larger garment |

Recorded and **not** gated at G1: median frame time, cold start to first frame, and the browser bundle
size. Startup and size are G5's exit criteria, and gating them here would settle a G5 question with a G1
harness.

## The decision rule

1. **R1 eligibility** — a topology is eligible for a profile only where the table above says it applies
   and it measured `capable = yes` there.
2. **R2 correctness** — any gate failure disqualifies the topology for that profile, and the verdict names
   the gate and the measured value. Correctness is never traded against speed.
3. **R3 scoring** — among survivors of one profile, the lowest `frame_p95_ms` wins. Two candidates within
   the 10 % margin are tied, and a tie is broken by lowest peak memory, then by the fewest unproven
   dependencies, then by name — so the rule is total and two readers get one answer.
4. **R4 one renderer where it is free** — a topology that survives in *both* profiles and is within the
   10 % margin of each profile's winner is chosen for both. Otherwise each profile takes its own winner and
   the record that closes the ADR must state the cost: two renderers, two conformance surfaces.
5. **R5 no survivor** — the question escalates to the director with the measurements attached, and the
   bounded fallback is the egui/iced dev shell (`G1-SLICE.14`) hosting the canvas for that profile until a
   re-spike. The product chrome waits; nobody improvises a fourth topology.
6. **R6 the verdict is derived** — `docs/tasks/artifacts/canvas_spike/run_spike_verdict.sh` reads the
   results and prints the verdict and the rule that produced it. A human may overrule only by a recorded
   decision that names the rows it overrules, which is governance §6.1's shape applied to a measurement.

## What the spike does not decide

The chrome, the dev-shell ruling and the TypeScript ban stand whatever the canvas measurement says: the ban
is enforced by CI on the front-end tree, and the dev shell exists precisely so the engine never blocks on
the hardest integration in the repository. A canvas result that surprises us changes a renderer, not an
architecture — and if it changes the architecture, that is a new ADR rather than a footnote here.

## What would reverse it

Three conditions, each needing a recorded decision: (1) the spike's measurements, which is the intended
path and needs no reversal of anything above; (2) a webview or WebGPU regression on a desktop OS that makes
an eligible topology incapable after the spike, which re-opens R1 for that profile; (3) "zero non-Rust"
becoming a hard constraint, which substitutes Slint for the chrome and re-runs the spike, because the
composition seam is a different one.
